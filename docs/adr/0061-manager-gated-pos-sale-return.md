# 0061. Expose a manager-gated "Return sale" (full refund) in the POS

- **Status:** Accepted
- **Date:** 2026-08-14
- **Deciders:** rifki, Claude (Opus 4.8)
- **Related:** [0006](0006-pos-payment-tenders.md) (payment tenders + `SaleRefunded`/`SaleVoided`), [0052](0052-preset-role-based-access.md) (preset role bundles, gateway-enforced), [0049](0049-two-app-outlet-terminal-program.md) P3b (device-terminal elevation), `docs/EVENT-CATALOG.md` (`SaleRefunded`)

## Context
A customer sometimes returns a purchase and must be refunded. The **backend for this already exists and is mature** (ADR 0006): `POST /api/v1/payments/{id}/refund` (restaurant-service) reverses a `CAPTURED` payment, emits `SaleRefunded`, and finance posts the GL reversal (dimensional + per-leg contra, read-model unwind); loyalty reverses earn/redeem. The gap was purely UI — no console surface exposed it (the `useRefundPayment` hook was dead code) — and the fleet-wide gateway route `/api/v1/payments/**` was gated to `POS_ROLES`, i.e. **a cashier could refund**.

The owner wants returns restricted to **manager**. Constraints: the gateway `RoleAuthorizationFilter` is the real authorization boundary (ADR 0052) — hiding a button is UX only; a POS sale carries exactly **one** payment (no split tender on the walk-in path), so "return the sale" = "refund its one payment"; refunds are **money-out** (rule 8 Money type) and **auth-sensitive**, so both correctness and role enforcement must be real, not cosmetic. Backend limitations are unchanged and inherited: **partial refunds are unsupported** (HTTP 400) and a **gift-card-settled sale cannot be fully refunded** (its residual reads as "partial").

## Decision
We expose a **full-sale return** in the POS, restricted to **`owner`/`manager`** (`SALE_REVERSAL_ROLES`), enforced at the **gateway**: a new `@Order(HIGHEST_PRECEDENCE)` route matches `/api/v1/payments/*/refund` and `/*/void` and applies `SALE_REVERSAL_ROLES`, ordered before the general `paymentsRoute` (which stays `POS_ROLES` for capture/receipt). The console surfaces a **"Return sale"** action on `ReceiptView` (both the post-sale receipt and the Sales-History reprint), shown only when the person is owner/manager **and** the payment is `CAPTURED` **and** the receipt is not an offline-provisional one; the refund is sent on the **personal/elevated bearer** (`auth: 'personal'`) so on a shared device terminal a cashier must hold an owner/manager **elevation** (ADR 0049 P3b) to proceed. **Out of scope (v1):** partial / per-item returns, gift-card-settled returns (surfaced as an honest error, not silently attempted), the servicepos/carwash `ServiceReceipt`, and any new refund endpoint, event, Avro schema, or migration — the existing refund path is reused unchanged.

## Consequences
- **Rule code now follows:** any money-reversal sub-path (`/refund`, `/void`) is `owner`/`manager` at the edge; capture and the receipt read stay `POS_ROLES`. The console mirrors this for UX (`rolePreset`-style owner/manager gate) but never as the boundary.
- **Enforced by:** the gateway integration test `GatewayRoleRoutingTest` (real Keycloak) — manager/owner reach `/refund` + `/void`, a cashier is `403` and the request never reaches restaurant-service, and the reversal route does not shadow `/capture` or `/receipt`. Frontend eligibility/error mapping is unit-tested (`returnSale.test.ts`).
- **Honest errors on a double-return:** a refund/void of an already-reversed payment is a domain STATE conflict — it now throws `PaymentNotReversibleException` (mapped to `409` by `config.PaymentAdvice`), NOT the shared catch-all `500`. This matters because the reversed sale can still read `CAPTURED` in the async register/history read models, so a manager (or a second terminal, or a lost-response retry) can re-attempt a return; the UI's `refundErrorKey` maps `409` to the honest "already returned / can't return in full" message instead of a misleading "please try again", and no spurious internal-error is logged. Regression: `PaymentTest.refundRejectedOnAlreadyRefundedSaleAsNotReversible`.
- **Easier:** managers can process a customer refund at the till with a GL-correct reversal and no back-office trip.
- **Costs / follow-ups:** partial and gift-card returns remain unsupported by design (the UI shows an honest "can't return in full" message on the backend 400) — the eventual path is a `SaleRefunded v2` with per-leg prorated amounts (see `PartialRefundNotSupportedException`). Bringing the same action to the servicepos `ServiceReceipt` is a follow-up. `void` is gated alongside `refund` for safety even though the UI standardizes on `refund` for the customer-return case.
